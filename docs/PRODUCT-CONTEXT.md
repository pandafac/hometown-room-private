## 2. 一句话产品定义

> 为第一次独自到访小地方的游客，提供基于店主授权资料回答问题的 AI 接待员；把游客问题回流成店主能看懂、能行动的经营信号与内容素材。

AI 不是全城导游，也不是店主分身。它负责双向翻译：

- 把店主知道的事实、菜单、礼仪和边界，翻译成游客能立即执行的到店建议。
- 把游客反复出现的疑问、担心和资料缺口，翻译成店主可以补充或用于内容创作的信息。

## 3. 核心问题

游客真正缺的不是“附近有什么地方”的列表，而是到了门口后仍不知道：

- 我一个人能不能进去？
- 应该怎么点、点多少？
- 坐哪里比较自然？
- 什么时候人少、什么时候会卖完？
- 店里有哪些礼仪、误解或不能承诺的事？
- 我接下来还能顺路去哪里？

店主则缺少：

- 持续解释自己店铺的时间和内容能力。
- 看见游客真实问题的渠道。
- 把已有知识转化成营销内容的低成本工具。

## 4. 核心用户与 JTBD

### 主用户：第一次到访的独行游客

典型情境：

- 独自旅行，愿意探索，但不想在门口反复犹豫。
- 看过攻略，仍然不知道哪家店适合自己。
- 预算、时间、天气、忌口或社交压力会影响选择。

功能 JTBD：

> 当我第一次来到陌生小镇，希望有人把一家店讲到我能直接行动的程度，从而不用反复搜索，也能自然走进去。

情感 JTBD：

- 获得确定感，避免“怕点错、坐错、问错”的焦虑。
- 感到自己被接待，而不是被营销。

### 供给方：独立小店店主

典型画像：

- 1–3 人小店，有真实故事与手艺。
- 没有时间持续做内容运营。
- 不愿意让 AI 冒充本人，也不愿承担不存在的承诺。

核心需求：

- 自己的店铺被准确理解。
- 游客问题被看见。
- 一次补充资料，可以持续改善之后的 AI 回答。

### 第三方视角的最终决定

产品曾讨论加入“本地讲述人”作为第三方角色，最终决定 Demo 2.0 不新增第三人入口、不新增第三方 AI。

保留的替代方案：

- 店主推荐下一站。
- 真实游客体验回声。

后续如恢复第三方视角，必须重新定义来源、授权和责任边界，不能只增加一个“本地人”AI 人设。

## 6. 信息架构与路由

### 身份入口

封面必须让用户在第一时间选择身份：

- 游客入口：找店、问答、拿到店卡。
- 店主入口：选店、补资料、看回声与生成内容。

禁止把游客聊天、店主资料编辑和经营数据混入同一入口。

### 游客路由

| 路由 | 页面职责 |
| --- | --- |
| `/` | 产品封面与身份选择 |
| `/visit` | 选择地区 |
| `/visit/:regionId` | 选择小镇 |
| `/visit/:regionId/:townId` | 小镇总览、店铺选择、场景入口 |
| `/room/:townId/:shopId` | 游客 AI 会客厅 |
| `/card/:townId/:shopId` | 第一次到店卡与体验回声 |

### 店主路由

| 路由 | 页面职责 |
| --- | --- |
| `/merchant` | 独立店主入口，选择地区、小镇和店铺 |
| `/merchant/:regionId/:townId/:shopId` | 店主工作台，默认打开店主资料 |

| `/merchant/...?...view=output` | 游客回声与内容输出视图 |

- `/room/:shopId` 自动跳转到带 `townId` 的新路由。

任何路由结构升级都要同步：

- `src/App.jsx`

## 7. 核心产品闭环

```text
店主资料输入
  -> AI 会客厅
  -> 游客问题
  -> 第一次到店卡
  -> 体验回声
  -> 商家回声板
  -> 补资料 / 生成内容
  -> 下一次回答变好
```

闭环的演示重点不是聊天本身，而是：

1. 游客问到一个资料缺口。
2. AI 明确承认缺口，不自行编造。
3. 商家看见该问题。
4. 店主补充一次资料。
5. 下一次回答使用“店主补充”内容。

## 8. 游客端交互

### 选择路径

游客先选择地区，再选择小镇，最后选择店铺。不要重新把三家或五家店堆回封面首页。

封面和游客目录提供统一搜索：

- 可按地区、小镇、店铺名称检索。
- 店铺同时匹配英文名、类别、简介与商品名。
- 结果按地区、小镇、店铺标注类型，直接进入现有页面。
- 游客浏览页提供“直接问店”快速入口，可按店名或小镇检索并直接进入现有 AI 会客厅；上次访问的店优先显示。支持 `Ctrl/⌘ + K` 打开，不新增或改变现有路由。
- 只有一个开放小镇的地区，地区卡会直接进入该小镇；面包屑与返回地区路径保留，不取消小镇层级。
- 小镇页将“今天的状态”确认放在店铺列表之前，与选店处于同一页面，不新增独立步骤；确认处境后仍可继续选择任意店铺。
- 小镇 hero 可使用来源明确的地方氛围图，但图片不替代状态、营业、价格或行动信息。
- 自定义“今天的状态”确认启用时，页面下方重复的旧处境列表隐藏，避免两个相似的选处境区域并存。
- 选中处境、需要或时间后，店铺卡片会按匹配度重新排序，并在首位标记“更符合今天”；所有店铺仍可选择。
- 处境卡片不是店铺链接：它负责排序右侧店铺并生成可编辑问题；只有点击店铺卡片才进入 AI 会客厅。
- 桌面端小镇选择采用左侧“今日状态 + 处境选择 + 问题草稿”、右侧“店铺选择”的工作区结构；页面整体上下滚动，手机端按相同顺序堆叠。
- 店铺卡顶部可用一张类型氛围缩略图帮助快速判断店铺气质，图片必须保持装饰/氛围属性，整卡点击和键盘焦点不受影响。

地区、小镇和开放店铺卡片整面可点击，底部动作文字只用于提示，不限制点击范围。筹备中内容保持禁用状态，不伪装为可进入。

### AI 会客厅

必须保留：

- 明确的 AI 接待员身份。
- “店主提供”的事实来源标记。
- 资料缺少时明确说“不知道”，并把问题留给店主。
- 追问建议。
- 生成到店卡入口。
- 回答生成期间允许游客继续输入下一问；下一问进入单一队列，不打断当前回答，并在当前回答结束后按顺序发送。
- 游客可在会客厅直接看到联系方式是否为店主已提供；未提供时明确标为资料缺口，不生成虚构号码。
- 会客厅店铺头图可使用对应店铺的氛围图，但 AI 面板宽度、正文阅读节奏和资料缺口提示不因配图改变。

建议追问不能只围绕菜单。应根据当前对话更新。

### 第一次到店卡

卡片包含六个行动模块：

1. 先怎么点。
2. 一个人坐哪里。
3. 可以问店主什么。
4. 一句本地表达。
5. 避开一个常见误会。
6. 店主推荐的下一站。

卡片必须可打印 / 保存 PDF / 保存为 PNG 图片。图片文件只包含到店卡本体，不包含导航、反馈表单和页面操作栏。

### 体验回声

- 游客可提交“哪一句真正帮到了我”。
- 需要匿名展示授权。
- 反馈是体验证据，不是客观事实。
- 不展示联系方式。

## 9. 店主端交互

店主工作台分为两个独立视图：

### 店主资料

- 查看 AI 已读取资料总数与分类。
- 浏览最近确认资料。
- 最近确认资料采用可扫读的三级层级：分类约 11px、问题约 15px、回答约 13px；不使用过小的 8–9px 正文。
- 桌面端最近确认资料的左侧分类与右侧问题按同一文字基线对齐；手机端保持分类在上、问答在下的自然阅读顺序。
- 回答待补问题。
- 待补问题卡分类约 11px、问题约 13px，卡片可点击区域不小于 44px。
- 自由新增知识。
- 新增资料必须经过“来自店主本人或授权资料”的确认。

访问端的今日状态来自店铺数据中的 `liveStatus`，不从 AI 回答推断。状态至少覆盖营业、客流和售罄三类，并使用图标与文字同时表达；Demo 不声称这些状态是实时数据。

### 游客回声

- 店主工作台首次进入默认打开“店主资料”；只有主动切换“游客回声”或使用 `?view=output` 时才进入经营输出视图。
- 查看高频问题聚类。
- 查看最近的匿名问题主题。
- 查看体验反馈。
- 查看未解决资料缺口。
- 生成营销内容。
- 游客回声页只保留一套内容生成区域；经营概览、资料补充与内容工坊使用清晰的分栏和纵向阅读顺序。

游客回声页只负责“看结果与行动”，资料文本输入只放在店主资料页。

## 10. AI 行为与质量控制

### 模型配置

- 提供方：DeepSeek
- 模型：`deepseek-flash`
- Base URL：`https://api.deepseek.com`
- 密钥环境变量：`DEEPSEEK_API_KEY`
- 密钥只允许存在：
  - `.env.local`
  - 用户明确授权的单文件交付 HTML 构建产物
  - 2026-11-08 到期前的专用 GitHub Pages 临时发布产物

禁止把密钥写入：

- README
- 本文件或其他 docs
- `AGENTS.md`
- 普通前端源码
- Git 公共仓库

### AI 回答边界

AI 必须：

- 只依据当前店铺的店主资料。
- 区分事实、体验反馈和 AI 整理。
- 不补充没有提供的价格、时间、库存、设施和承诺。
- 不冒充店主。
- 资料缺少时标记 `missing` 或 `partial`。
- 对最后一轮游客问题直接作答。

### 回答质量保护

核心实现：

- `server/quality.js`
- `src/standalone/shim.js`

流程：

1. 识别最后一条游客问题的意图。
2. 支持多意图，例如“一个人来，怎么点？”同时包含独行与菜单。
3. 把意图写入提示词。
4. AI 返回后校验回答是否覆盖所有意图。
5. 跑题时使用本地资料回退回答。
6. 单文件版在返回回答前再次逐项检查全部意图；若模型或本地回退漏答，会补齐缺失主题、来源标签和资料缺口后再展示。

必须长期保留的回归用例：

```text
游客：下午四点需要排队吗？
AI：面馆已收门，并说明营业时间。

游客：哦，那什么时候排队的人多？我是不是得早一点来？
AI：周末 11:20–12:30 最挤；
    工作日 10:30 前或 12:50 后更合适。
```

上线前禁止出现：

> 用户追问排队时间，AI 返回“第一次来建议点什么”。

- `server/runtime.js` 负责归一化地区、小镇、店铺、场景和商家种子数据。
- 服务端开发模式使用进程内存保存问答、反馈和补充资料，重启后恢复种子状态。
- 单文件版使用浏览器 `localStorage` 保存用户补充和反馈，刷新后仍保留。

### 数据规则

- 预置体验回声必须标记 `simulated: true`。
- 真实反馈不得采集联系方式。
- 体验回声不能作为营业事实来源。
- 店主资料是回答事实的唯一依据。

## 13. 单文件交付架构

### 生成命令

```powershell
node scripts/patch-demo3-ui.mjs
```

### 核心机制

- `scripts/patch-demo3-ui.mjs` 对归档的 Demo 3.0 HTML 做增量补丁。
- 补丁后的 HTML 生成 `outputs/`、`deliverables/` 与 GitHub Pages 发布文件。
- 使用 `sharp` 将 28 张内联 PNG/JPEG 转换为 WebP；当前图片从 39.0 MB 降至 8.3 MB。
- 全部 CSS、JS、数据和 DeepSeek 配置仍内联在一个约 12.0 MB 的 HTML。
- 使用 `HashRouter`，保证 `file://` 也能切换页面。
- `src/standalone/shim.js` 拦截 `/api/*`，在浏览器内提供：
  - bootstrap
  - chat
  - arrival card
  - feedback
  - merchant dashboard
  - gap answer

## 15. 已知限制

- 单文件依赖现代浏览器支持 `fetch`、`Response`、`structuredClone`、`localStorage`。
- 文件版 AI 直接访问 DeepSeek，依赖外网和 Key 可用性。
- 文件版数据只保存在当前浏览器；队友之间不同步。
- 原 GitHub Pages 公开入口已于 2026-11-09 下线；仓库已私有化，发布分支已删除。
- 静态部署入口现在从同目录加载版本化内容包，不依赖第三方 GitHub CDN 或代理。
- 服务端版动态数据只保存在当前 Node 进程，重启恢复种子。
- 产品没有数据库、账号体系、权限管理、支付或真实店主认证。
- 当前所有店铺和人物均为虚构。
- 当前没有公开访问地址；重新上线必须先加入访问控制和浏览器端密钥替代方案。
- 当前工作区已迁移到 `D:\Guest's Home`，存在 Git 仓库但尚无提交；本次迁移未创建 commit。
- 联系方式尚无独立结构字段，因此当前分享版明确显示“店主尚未提供”；后续应由店主资料表单正式补充。
- 店铺收藏、价格筛选和完整标签筛选暂不进入当前版本。应先统一店主确认的标签数据源，再增加筛选界面，避免空标签或无依据标签。
